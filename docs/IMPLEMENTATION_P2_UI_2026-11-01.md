# تنفيذ واجهة ملفات الشراء P2 — مرشح 0.1.7-beta.1

**التاريخ:** 01/11/2026. **الحالة:** شيفرة مرشح قبل القبول الميداني؛ الاختبارات والبناء لا تثبت نجاح الواجهة على HP 630 تلقائيًا.

## الوظائف الجديدة

- تبويب GTK عربي باسم **«متطلباتي»** مع وضع عام افتراضي لا يتطلب إعدادًا، ووضع اختياري مخصص يطبق قواعد P2 بعد اكتمال L1.
- إدخال اسم ملف المتطلبات، RAM المركبة، العدد المنطقي للمعالجات، سعة التخزين الاسمية، اشتراط SSD، الميزانية (DZD)، مدة الضمان الدنيا، مجال/مجالات العمل، ومزاعم البائع عن الموديل وRAM.
- إدخال سعر العرض الفعلي والضمان المصرح به **كمدخلات مؤقتة**؛ لا تُعد قياسات للفاحص، ولا تُحسب تقييمًا لسعر السوق.
- زر **«تطبيق المتطلبات»** يغيّر الحكم الشخصي فقط. تغيير أي حقل دون الضغط عليه لا يغيّر القرار المطبق.
- تصدير ملف المتطلبات JSON للحافظة، واستيراده منها بعد تحقق المخطط؛ **واستيراد ملف JSON موجود بالفعل عبر منتقي ملفات للقراءة فقط** مع رفض الروابط الرمزية والملفات الخاصة والملفات الأكبر من 64 KiB. يمكن إعداد الملف خارج المحل ونسخه إلى USB.
- حفظ ملف المتطلبات JSON في `PC-Inspector-Profiles/` على قسم USB مؤكد أنه USB فعلي، منفصل كليًا عن `PC-Inspector-Reports/`، ثم قراءة القائمة واستيراد ملف محفوظ. أسماء الملفات مولّدة عشوائيًا ولا يمرّ أي مسار يحدده المستخدم إلى المساعد ذي الصلاحيات المرتفعة.
- عند تشغيل الملف المخصص، تعرض واجهة GTK مقارنة محاور P2؛ وعند حفظ تقرير الجلسة ينشئ التطبيق **نسخة مشتقة من قاموس التقرير** تتضمن `buyer_profile` و`buyer_offer` و`buyer_profile_assessment`، ويولّد HTML قسمًا إضافيًا موثق المصدر. لا تتغير الحقول الخام `storage` أو `health_assessment` أو `purchase_assessment` أو `schema_version=1`.
- الوضع العام يحفظ نفس بنية التقرير السابقة دون حقول تخصيص؛ الهاتف والإنترنت غير مطلوبين.

## بروتوكول الأمان

الملف التنفيذي `/usr/local/bin/pc-inspector-profiles` يسمح **فقط** بعمليات `save` و`list` و`load`، ويستعمل `usb_store.report_destination()` للتحقق من أن الهدف USB واسم القسم ونوع نظام الملفات ومصدر التركيب. الكتابة تستخدم `O_EXCL` و`O_NOFOLLOW` مع مجلد مستقل و`fsync` ومقارنة القراءة بالبيانات المرسلة ثم SHA-256. لا يحذف أي ملف سابق، ولا يقبل مسارات عشوائية أو ملفات أكبر من 64 KiB. التنزيل من USB يرفض الروابط الرمزية والملفات غير المنتظمة والبيانات غير الصالحة.

**قيد تشغيلي:** إذا لم يمكن تركيب قسم PCINSPDATA أو Ventoy الموثق للكتابة فلا يُزعم نجاح التصدير. يبقى الملف في الذاكرة ويمكن نسخه للحافظة. لا يغيّر البرنامج الأقراص الداخلية ولا يهيئ USB.

## حدود ما نفذ وما لم ينفذ

- أداة P2 تعتمد محرك P1 الحالي، ولا تستنبط قدرات معالج أو GPU من رقم الطراز دون دليل.
- لا يوجد تقييم لقيمة سعر السوق، ولا مصادقة على أن ضمان البائع فعلي أو صحيح.
- لا توجد قاعدة بيانات عروض أو مقارنة تجارية شاملة متعددة الأجهزة في واجهة مستقلة بعد؛ يمكن استعمال ملف متطلبات واحد لمقارنة فحوص متعددة يدويًا.
- لم تضف وظائف P3 لنقل البيانات إلى الهاتف.
- ما زالت اختبارات D/G المستقلة وUEFI والحاسوب دون قرص مطلوبـة.

## اختبارات قبول مطلوبة

1. Python + GTK virtual-display CI ناجحة (تشمل إنشاء الواجهة في الوضع العام والملف المخصص، وعدم تعديل التقرير الخام).
2. اختبارات تصدير/استيراد USB على مجلد مؤقت ومعاينة SHA-256 وعدم تغيير تقارير سابقة ورفض الروابط الرمزية.
3. ISO CI ناجحة مع التحقق من تثبيت المساعد والصلاحيات المحدودة.
4. **اختبار ميداني لاحق:** صورة تبويب «متطلباتي» بالعربية ومحاذاة حقيقية يمينية، تطبيق ملف متطلبات على HP 630 مع استمرار `do_not_buy` بسبب SMART، حفظ تقرير مخصص واسترجاعه وفحص البصمات ومقارنة ملف المتطلبات. لا تكرر اختبار إجهاد أو B السابق.

**حكم القبول الحالي:** غير محسوم حتى نجاح CI والاختبار الميداني اللاحق.

**تحسين التحقق من إعلان الموديل:** إذا صرّح البائع باسم مختصر مثل `HP 630` وأبلغ DMI عن `HP 630 Notebook PC`، تكون المطابقة الجزئية `needs_verification` لا `fail` ولا `pass`؛ اختلاف رقم الطراز مثل `HP 650` يبقى اختلافًا صريحًا. لا تُستنتج أصالة الجهاز من مطابقة الأسماء.

# USB-PC-Inspector — التصميم المعماري المعتمد

> الحالة: **تصميم معتمد / تنفيذ تدريجي مخطط** — 27/10/2026. لا يعني اعتماد التصميم أن الميزات الجديدة منفذة أو مختبرة.

## 1. الرؤية والقرار الأساسي

USB-PC-Inspector منظومة مستقلة عن نظام التشغيل المثبت على الحاسوب، تقلع من USB، وتساعد على اتخاذ ثلاثة قرارات: **هل أشتري الجهاز؟ هل أحتاج إلى التعمق قبل الدفع؟ هل أحتفظ بالجهاز أم أرجعه خلال فترة التجربة؟**

الهدف العملي: **معلومات مفيدة بسرعة أولًا، ثم تعمق اختياري متدرج**. يجب ألا يؤخر الاتصال بالهاتف أو الذكاء الاصطناعي أو فحص طويل عرض النتائج الأولية. يعمل التطبيق في **الوضع العام دون أي تحضير**؛ وملف المتطلبات المحضر في البيت **اختياري بالكامل**.

### مبادئ ملزمة
1. Offline-first؛ لا إنترنت مطلوب للفحص أو التقرير الأساسي أو التحكم المحلي.
2. Read-only افتراضيًا: لا كتابة على الأقراص الداخلية ولا تغيير firmware، ولا اختبارات ضغط/كتابة دون إذن واضح.
3. كل استنتاج يرتبط بأدلة وحدود ثقة؛ عدم وجود بيانات لا يعني سلامة الجهاز.
4. الفصل بين **مطابقة الإعلان** و**الحالة التقنية** و**ملاءمة الاستخدام** و**الجدوى الاقتصادية**.
5. فصل جمع البيانات والتشخيص الحتمي عن الواجهة، والهاتف، والوكيل الذكي.
6. استقلال الفحص عن اتصال الهاتف والسحابة؛ لا تفشل الجلسة بانقطاع الشبكة.
7. لغة عربية RTL أولًا، والتواريخ المعروضة dd/mm/yyyy.
8. الأجهزة المستهدفة أولًا x86_64 BIOS/UEFI، مع دعم الإقلاع دون قرص داخلي.

## 2. أوضاع الاستخدام

### أ. الوضع العام (الافتراضي)
- إقلاع USB، بدء الجرد الآمن، عرض النتائج تدريجيًا.
- لا يُطلب ملف شراء أو حساب أو اتصال هاتف أو شبكة.
- يمكن إدخال السعر والضمان والاستخدامات عند الحاجة، أو الاكتفاء بالحالة التقنية.
- النتيجة الأولية قد تكون: **مرشح مبدئيًا / افحص قبل الدفع / لا يُنصح بالشراء / غير محسوم**؛ لا يصدر حكم سعري دون سعر ومرجع مقارنة.

### ب. الوضع المخصص (اختياري)
- إعداد ملف شراء في المنزل أو على الهاتف أو في المحل، ثم حفظه/استيراده.
- الحقول: ميزانية وسعر مستهدف وعملة؛ حالة الجهاز المعلنة؛ الاستخدامات والأولويات؛ حد أدنى/مفضل للمواصفات؛ مدة الاستفادة؛ ضمان وإرجاع؛ شروط إقصائية؛ اختبارات مفضلة.
- الملف JSON مستقل بإصدار schema، مع تحقق من صحة البيانات وترحيل الإصدارات.
- يمكن تعديل الملف أثناء الجلسة دون تغيير النسخة الأصلية، وإعادة استعماله لمقارنة عدة أجهزة.

## 3. درجات الفحص وقراراتها

| الدرجة | الهدف الزمني بعد الإقلاع (غير مضمون) | النطاق | القرار |
|---|---|---|---|
| L1 فوري | 10–30 ثانية | BIOS/DMI، CPU، RAM، الأقراص، SMART المتاح سريعًا، البطارية إن توفرت، مقارنة المواصفات | شراء مبدئي/تحذير/تعمق |
| L2 سريع موسع | 2–5 دقائق | SMART تفصيلي، حرارة، بطارية، فحوص تفاعلية للشاشة/لوحة المفاتيح/المنافذ/الشبكة | تقليل الشك قبل الدفع |
| L3 معمق | 15–30 دقيقة أو أكثر | فحوص RAM وقراءة غير مدمرة للتخزين واستقرار/حرارة بموافقة | احتفاظ/إرجاع |
| L4 استقصائي | ساعة أو أكثر | فحوص مطولة وتحليل أخطاء متقطعة ومقارنة الجلسات | حسم الحالات الملتبسة |

هذه أهداف أداء قابلة للقياس وليست تعهدًا بالزمن. كل درجة تضيف أدلة ولا تعيد العمل المنجز دون داع. الاختبارات غير المتاحة أو غير المنفذة تبقى ظاهرة في التقرير. يجب فصل **حالة تنفيذ الاختبار** (مكتمل/جزئي/لم ينفذ/غير مدعوم/فشل التنفيذ) عن **التقييم الفني** (سليم وفق الأدلة/تحذير/خلل/غير محسوم).

## 4. المكونات المعمارية

```text
USB Live (Debian)
  ├── Inspector Core
  │   ├── Collectors: CPU / DMI / RAM / disks / SMART / battery / network / sensors
  │   ├── Test Orchestrator: queues, progress, cancellation, consent, timeouts
  │   ├── Evidence Store: normalized facts + raw outputs + timestamps + provenance
  │   ├── Deterministic Diagnostic Rules: findings, severity, confidence
  │   ├── Purchase Decision Engine: requirements, suitability, price, warranty
  │   └── Report & USB Export: JSON, HTML, later PDF
  ├── Desktop UI: existing Tkinter prototype → improve or replace after evaluation
  ├── Local Companion Service: authenticated API + progress events + file transfer
  └── Optional Remote Desktop: separately enabled and authorized
             ↕ Wi-Fi LAN / phone hotspot / supported AP mode
Android Inspector Mobile
  ├── Pairing & local discovery
  ├── Live dashboard & test control
  ├── Profiles, prices, notes, reports, device comparison
  └── Optional AI Agent client
             ↕ optional network, explicit permission
AI Agent / model provider (cloud or future on-device)
```

**لا يُفترض أن الواجهة الحالية Web UI**: المستودع يحتوي حاليًا على Tkinter. تُراجع إمكانية إبقائها في بيئة Live مع تقديم واجهة ويب للهاتف عبر الخدمة المحلية، أو الانتقال إلى واجهة مشتركة لاحقًا، بناءً على الكلفة والتوافق.

### حدود الصلاحيات
- Collectors لا تنفذ إلا عمليات قراءة معلومة.
- الاختبارات تستخدم allowlisted commands بوسيطات متحقق منها، ولا تمرر shell عامًا.
- خدمة الهاتف ليست ذات صلاحيات root؛ تتواصل مع orchestrator عبر واجهة محكومة.
- عمليات الضغط/الفحوص الطويلة تتطلب موافقة صريحة ووقتًا محددًا وإلغاءً وحدودًا حرارية.
- Agent **لا يمتلك shell ولا حق تعديل الملفات الداخلية**، ويقترح الأفعال؛ التنفيذ محصور في أدوات مسموحة وبإذن المستخدم حيث يلزم.

## 5. Inspector Mobile والاتصال اللاسلكي

تطبيق Android مستقل مخطط له، مع **واجهة متصفح محلية بديلة** للتوافق والتجربة المبكرة. لا يفترض اتصال إنترنت أو حسابًا سحابيًا.

### خيارات الشبكة بالترتيب العملي
1. الاتصال بالشبكة المحلية نفسها أو بنقطة اتصال الهاتف؛ إن توفرت بطاقة Wi-Fi وتعريفاتها.
2. إنشاء نقطة وصول من الحاسوب إذا دعم المحول وضع AP.
3. بديل محلي سلكي أو حفظ التقرير على USB عند غياب Wi-Fi.

الاقتران عبر QR يحتوي عنوان الخدمة ورمزًا مؤقتًا، مع تأكيد بصري على الجهازين، ورمز جلسة محدود الصلاحيات. لا يفتح الخادم خدماته للعامة. تُستخدم قناة مشفرة ومصادقة جلسة وتحقق من صلاحية الطلبات، مع تدوير/إبطال الرموز عند انتهاء الجلسة. تُدرس آلية الثقة بالشهادة في شبكة بلا إنترنت دون تجاوز التحقق الأمني.

### وظائف الهاتف
- عرض البيانات والتقدم والتحذيرات فور وصولها.
- تنزيل JSON/HTML/PDF عندما يتاح التصدير؛ واستيراد ملف شراء/سعر/ملاحظات.
- طلب اختبارات مسموحة وإيقافها؛ مع الموافقة المحلية على العمليات الحساسة.
- حفظ تقارير الأجهزة ومقارنتها دون اتصال.
- **التحكم في التطبيق أولًا**؛ مشاركة الشاشة والفأرة/لوحة المفاتيح لاحقًا، بتمكين صريح وجلسة مؤقتة (مثل VNC مؤمن أو بديل مناسب). لا تفتح remote desktop افتراضيًا.
- النقل يستأنف أو يعيد المحاولة بعد انقطاع الشبكة؛ ملفات التقرير تتحقق من الحجم والبصمة.

### واجهة API مبدئية (غير منفذة)
- `GET /api/v1/session` حالة الجلسة والإصدار.
- `GET /api/v1/inventory` جرد الجهاز.
- `GET /api/v1/findings` الأدلة والاستنتاجات.
- `GET /api/v1/tests` قائمة الفحوص ودعمها.
- `POST /api/v1/tests/{id}/start` طلب فحص مع تحقق الصلاحية/الموافقة.
- `POST /api/v1/tests/{id}/cancel` إلغاء فحص.
- `GET /api/v1/events` بث حالة الفحص (SSE أو WebSocket).
- `GET /api/v1/reports/{id}` تنزيل تقرير مصرح به.
- `POST /api/v1/profiles` استيراد ملف شراء متحقق منه.

تخضع أسماء المسارات للمراجعة قبل التثبيت؛ يمنع كشف أرقام الأجهزة التسلسلية في الواجهة الخارجية دون خيار خصوصية.

## 6. AI Agent — دور مقيد بالأدلة

**الطبقة الأساسية حتمية وتعمل دون AI.** يقرأ الوكيل نتائج الفحص والأدلة والمواصفات والميزانية والضمان والسعر، ثم:
- يشرح نتائج SMART والأخطاء والتعارضات.
- يجيب: هل يناسب البرمجة/المكتب/التصميم/الألعاب؟ مع بيان القيود.
- يقترح الاختبار التالي الأكثر قيمة قياسًا بالوقت والمخاطرة.
- يساعد في مقارنة العروض وصياغة تقرير الاحتفاظ/الإرجاع.
- يميز الوقائع المقاسة من الاستنتاجات والافتراضات، ويذكر البيانات الناقصة.

لا يُسمح للوكيل باختلاق بيانات جهاز أو اعتبار تقرير لغوي دليلًا تشخيصيًا. الخدمة السحابية **اختيارية** وتتطلب موافقة واعية على نوع البيانات المرسلة؛ تُحجب المعرفات الحساسة افتراضيًا. تشغيل نموذج محلي على الهاتف/الحاسوب مسار بحثي يخضع لاختبارات أداء، وليس متطلبًا للنسخة الأولى.

## 7. نماذج البيانات وقرارات الشراء

**InspectionSession**: session_id، UTC timestamp، build_version، boot environment، device fingerprints متعددة، profile_id اختياري، test executions، evidence، findings، reports.

**Finding**: code، component، severity، verdict، confidence، evidence references، observed_at، limitations، recommended_next_test.

**PurchaseAssessment** أربعة محاور مستقلة:
1. مطابقة إعلان البائع.
2. الحالة التقنية.
3. الملاءمة لاستخدامات محددة وقابلية الترقية والاستدامة.
4. السعر والضمان والمقارنة السوقية **فقط عند توفر مرجع موثوق وحديث**.

لا تُدمج هذه المحاور في «نسبة صحة» مضللة. لا تعني ساعات تشغيل القرص عمر الجهاز أو إثبات أنه جديد؛ ولا تعني نتيجة SMART القديمة سلامته الحالية. لا يُفسر غياب البطارية على أنه عطل. يُحفظ سجل فحص قبل الشراء وبعده لمقارنة الأدلة وإصدار قرار **احتفظ/أرجع/افحص أكثر** مع توضيح أن حق الإرجاع تحدده شروط البيع والقانون.

## 8. السلامة والتخزين والتقارير

- لا تكتب على الأقراص الداخلية؛ تحقق من USB المستهدف قبل الحفظ.
- عند تعذر الحفظ، أخبر المستخدم ولا تدّع نجاحه؛ يمكن النقل إلى الهاتف بعد الاقتران.
- افصل وسيط Live للقراءة عن قسم بيانات قابل للكتابة؛ اختبر Ventoy ومفتاح USB المخصص عمليًا.
- UTF-8 صحيح، دعم العربية RTL، وتواريخ dd/mm/yyyy في العرض؛ ISO 8601/UTC في البيانات الآلية.
- JSON مصدر الحقيقة، HTML تقرير محلي، PDF لاحقًا؛ تضمين نسخة schema والتوقيتات وحالة الاختبارات والأدلة وقيودها.
- لا يتم تشغيل خدمات الشبكة أو سطح المكتب قبل طلب المستخدم أو تفعيل سياسة واضحة؛ الاتصال بالهاتف اختياري.

## 9. معايير قبول عابرة للمكونات

1. فحص L1 دون إعداد مسبق أو إنترنت أو هاتف، مع نتائج تدريجية قابلة للفهم.
2. إظهار نتيجة «غير محسوم» عند نقص أدلة جوهرية بدل اختلاق حكم.
3. عدم كتابة أي بايت إلى أقراص الجهاز الداخلية أثناء الفحص الافتراضي.
4. عمل الجلسة وحفظ نتائجها عند انقطاع Wi-Fi أو غياب بطاقة لاسلكية.
5. اقتران هاتف مصرح به فقط، وتنزيل تقرير مطابق للأصل، وإبطال الاقتران عند انتهاء الجلسة.
6. فحوص إضافية بموافقة، قابلة للإيقاف، مع حدود وقت/حرارة حيث ينطبق.
7. اختلاف القرار بحسب ملف الاستخدام والسعر دون تغيير الحكم على السلامة التقنية.
8. اختبار الإقلاع والحفظ فعليًا على Legacy BIOS وUEFI، وبوجود/غياب قرص داخلي.
